\section[Diagrama Entidad-Relación (ER)]{\emj{🧠}~Diagrama Entidad-Relación (ER)}

El modelo ER es una herramienta conceptual: permite capturar la estructura del dominio de negocio antes de pensar en tablas, tipos de datos o índices.
Es independiente del DBMS y sirve como lenguaje común entre desarrolladores y stakeholders.
Una vez validado el modelo ER, el paso a SQL (DDL) es casi mecánico.

\begin{teoriabox}{Elementos del modelo ER}
\begin{itemize}
  \item \textbf{Entidad:} objeto del mundo real con existencia propia (rectángulo en Chen)
  \item \textbf{Atributo:} propiedad de la entidad (elipse en Chen / columna en Crow's Foot)
  \item \textbf{Relación:} asociación semántica entre entidades (rombo en Chen, línea en Crow's Foot)
  \item \textbf{Entidad débil:} depende de otra para existir; sin PK propia, usa \textbf{llave parcial} combinada con la PK del padre
  \item \textbf{Cardinalidad:} cuántas instancias de una entidad se relacionan con la otra (1:1, 1:N, M:N)
\end{itemize}
El proceso: identificar entidades → definir atributos → establecer relaciones → asignar cardinalidades → verificar con casos de uso reales.
\end{teoriabox}

\section[Notaciones]{\emj{📋}~Notaciones}

Existen varias notaciones para diagramas ER; todas expresan lo mismo con símbolos distintos.
La notación Chen es más académica y explícita; Crow's Foot es el estándar en herramientas de producción.

\begin{itemize}
  \item \textbf{Chen:} rectángulos, rombos, elipses. Académica, verbosa, mejor para aprendizaje.
  \item \textbf{Crow's Foot:} líneas con símbolos de cardinalidad en extremos. Estándar en herramientas (Lucidchart, dbdiagram.io, DBeaver).
  \item \textbf{UML Clases:} atributos y métodos en compartimentos. Útil cuando el modelo de datos y el de objetos son lo mismo (ORM).
\end{itemize}

\section[Cardinalidad en Crow's Foot]{\emj{🔗}~Cardinalidad en Crow's Foot}

La notación Crow's Foot combina dos elementos en cada extremo de la línea: la \textbf{modalidad} (si la participación es obligatoria u opcional) y la \textbf{cardinalidad} (uno o muchos).
Se leen desde el centro de la relación hacia afuera.

\begin{itemize}
  \item \texttt{||} exactamente uno (obligatorio)
  \item \texttt{|o} cero o uno (opcional)
  \item \texttt{||<} uno o muchos (obligatorio)
  \item \texttt{|o<} cero o muchos (opcional)
\end{itemize}

\begin{lstlisting}[caption={DDL derivado del modelo ER}]
CREATE TABLE clientes (
    id     SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    email  VARCHAR(200) UNIQUE NOT NULL
);

CREATE TABLE productos (
    id     SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    precio NUMERIC(10,2) NOT NULL CHECK (precio >= 0)
);

CREATE TABLE pedidos (
    id          SERIAL PRIMARY KEY,
    id_cliente  INTEGER NOT NULL REFERENCES clientes(id),
    fecha       TIMESTAMP DEFAULT NOW(),
    estado      VARCHAR(20) DEFAULT 'pendiente'
);

CREATE TABLE pedido_items (
    id_pedido   INTEGER REFERENCES pedidos(id)   ON DELETE CASCADE,
    id_producto INTEGER REFERENCES productos(id) ON DELETE RESTRICT,
    cantidad    INTEGER NOT NULL CHECK (cantidad > 0),
    precio_unit NUMERIC(10,2) NOT NULL,
    PRIMARY KEY (id_pedido, id_producto)
);
\end{lstlisting}

\begin{lstlisting}[caption={Consulta con JOIN múltiple}]
SELECT p.id AS pedido, c.nombre AS cliente,
       pr.nombre AS producto, pi.cantidad, pi.precio_unit
FROM   pedidos p
JOIN   clientes c      ON p.id_cliente = c.id
JOIN   pedido_items pi ON pi.id_pedido = p.id
JOIN   productos pr    ON pi.id_producto = pr.id
WHERE  p.estado = 'pendiente'
ORDER BY p.fecha DESC;
\end{lstlisting}
