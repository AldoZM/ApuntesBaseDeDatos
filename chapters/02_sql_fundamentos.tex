\chapter[SQL Fundamentos]{\emj{💻}~SQL Fundamentos}

\section[Sublanguages SQL]{\emj{🧠}~Sublanguages SQL}

SQL (Structured Query Language) es un lenguaje \textbf{declarativo}: describes \emph{qué} resultado quieres, no \emph{cómo} calcularlo.
El motor de base de datos recibe tu consulta, la analiza, genera un plan de ejecución óptimo y lo ejecuta.
Esta abstracción es poderosa: el mismo SQL puede ejecutarse de formas físicas completamente distintas dependiendo de los índices disponibles, el tamaño de las tablas y las estadísticas del optimizador.

SQL se divide en cinco sublanguages según el tipo de operación que realizan.
Conocer esta división ayuda a entender qué efecto tiene cada comando y si puede o no revertirse con un ROLLBACK.

\begin{teoriabox}{Los cinco sublanguages de SQL}
\begin{itemize}
  \item \textbf{DDL} (Data Definition Language): define la \emph{estructura} del esquema.
    \texttt{CREATE, ALTER, DROP, TRUNCATE, RENAME}. En la mayoría de DBMS es auto-commit (no revertible), pero en PostgreSQL el DDL sí es transaccional.
  \item \textbf{DML} (Data Manipulation Language): manipula los \emph{datos} dentro de las estructuras.
    \texttt{INSERT, UPDATE, DELETE, MERGE}. Siempre dentro de una transacción; reversible con ROLLBACK.
  \item \textbf{DQL} (Data Query Language): consulta datos sin modificarlos.
    \texttt{SELECT}. El comando más complejo y usado de SQL.
  \item \textbf{DCL} (Data Control Language): controla \emph{permisos} de acceso.
    \texttt{GRANT, REVOKE}. Define quién puede hacer qué sobre qué objetos.
  \item \textbf{TCL} (Transaction Control Language): gestiona \emph{transacciones}.
    \texttt{BEGIN, COMMIT, ROLLBACK, SAVEPOINT, RELEASE SAVEPOINT}.
\end{itemize}
La distinción entre DDL y DML importa porque un \texttt{DROP TABLE} en la mayoría de DBMS no puede revertirse aunque estés dentro de una transacción. PostgreSQL es la excepción: su DDL transaccional permite \texttt{ROLLBACK} de un \texttt{DROP TABLE}.
\end{teoriabox}

\section[DDL --- definir estructura]{\emj{🏗️}~DDL --- definir estructura}

El DDL define el \textbf{esquema}: la estructura de las tablas, sus columnas, tipos de datos y las reglas (constraints) que gobiernan qué valores son válidos.
Un buen esquema con constraints bien definidos es la primera línea de defensa de integridad de datos: previene datos inválidos a nivel de motor, sin depender de que la aplicación los valide correctamente.

Los \textbf{constraints} son reglas que el DBMS enforcea en cada operación:
\begin{itemize}
  \item \texttt{PRIMARY KEY:} identifica unívocamente cada fila; NOT NULL + UNIQUE implícitos
  \item \texttt{UNIQUE:} no permite valores duplicados en la columna o combinación de columnas
  \item \texttt{NOT NULL:} la columna debe tener valor; nunca puede ser NULL
  \item \texttt{CHECK:} condición booleana que cada valor debe cumplir (ej. \texttt{precio > 0})
  \item \texttt{DEFAULT:} valor que se usa si no se especifica uno en el INSERT
  \item \texttt{FOREIGN KEY:} establece relación con otra tabla; garantiza integridad referencial
\end{itemize}

\texttt{ALTER TABLE} permite modificar la estructura de una tabla existente sin recrearla.
En tablas grandes (millones de filas), algunas operaciones de ALTER pueden ser costosas porque requieren reescribir toda la tabla o bloquear escrituras durante la operación.
Agregar una columna nullable es barato; agregar una columna NOT NULL sin DEFAULT requiere actualizar cada fila existente.

\section[DML + DQL --- manipular y consultar]{\emj{🔎}~DML + DQL --- manipular y consultar}

El \texttt{SELECT} es el comando más complejo de SQL porque su sintaxis no refleja el orden en que se ejecuta.
Se escribe en el orden: SELECT → FROM → WHERE → GROUP BY → HAVING → ORDER BY → LIMIT.
Pero el motor lo evalúa en un orden completamente distinto, y entender ese orden es crítico para evitar errores y escribir consultas eficientes.

\begin{tipbox}{Orden lógico de evaluación de SELECT}
El motor evalúa en este orden:
\begin{enumerate}
  \item \texttt{FROM} + \texttt{JOIN}: determina el conjunto de filas base
  \item \texttt{WHERE}: filtra filas del conjunto base (opera sobre columnas reales, no aliases)
  \item \texttt{GROUP BY}: agrupa las filas filtradas
  \item \texttt{HAVING}: filtra grupos (puede referenciar funciones de agregación)
  \item \texttt{SELECT}: calcula las expresiones y aliases de salida
  \item \texttt{ORDER BY}: ordena el resultado (puede usar aliases del SELECT)
  \item \texttt{LIMIT / OFFSET}: recorta el resultado final
\end{enumerate}
Consecuencia práctica: no puedes usar un alias definido en \texttt{SELECT} dentro de \texttt{WHERE}, porque WHERE se evalúa antes. Pero sí puedes usarlo en \texttt{ORDER BY}.
\end{tipbox}

Los \textbf{JOINs} combinan filas de dos tablas según una condición.
El tipo de JOIN determina qué pasa cuando no hay coincidencia:
\begin{itemize}
  \item \textbf{INNER JOIN:} solo filas que coinciden en ambas tablas. Excluye los que no tienen par.
  \item \textbf{LEFT JOIN:} todas las filas de la tabla izquierda; NULL en columnas de la derecha si no hay coincidencia.
  \item \textbf{RIGHT JOIN:} todas las filas de la derecha; NULL en la izquierda si no hay coincidencia. (Equivalente a LEFT JOIN con tablas invertidas.)
  \item \textbf{FULL OUTER JOIN:} todas las filas de ambas tablas; NULL donde no hay coincidencia.
  \item \textbf{CROSS JOIN:} producto cartesiano — cada fila de la izquierda con cada fila de la derecha.
\end{itemize}

\begin{lstlisting}[caption={DDL: CREATE, ALTER, DROP}]
-- Crear tabla con constraints
CREATE TABLE clientes (
    id        SERIAL PRIMARY KEY,
    email     VARCHAR(200) NOT NULL UNIQUE,
    nombre    VARCHAR(100) NOT NULL,
    activo    BOOLEAN DEFAULT TRUE,
    creado_en TIMESTAMP DEFAULT NOW()
);

-- Agregar columna
ALTER TABLE clientes ADD COLUMN telefono VARCHAR(20);

-- Agregar constraint después de crear
ALTER TABLE clientes ADD CONSTRAINT chk_email CHECK (email LIKE '%@%');

-- Eliminar columna
ALTER TABLE clientes DROP COLUMN telefono;
\end{lstlisting}

\begin{lstlisting}[caption={DML: INSERT, UPDATE, DELETE}]
-- INSERT con RETURNING (PostgreSQL)
INSERT INTO clientes (email, nombre)
VALUES ('ana@ejemplo.com', 'Ana López')
RETURNING id, creado_en;

-- UPDATE con condición
UPDATE clientes
SET    activo = FALSE
WHERE  creado_en < NOW() - INTERVAL '1 year'
  AND  activo = TRUE;

-- DELETE con subquery
DELETE FROM clientes
WHERE id IN (
    SELECT id FROM clientes
    WHERE activo = FALSE
    ORDER BY creado_en
    LIMIT 100
);
\end{lstlisting}

\begin{lstlisting}[caption={SELECT con JOINs}]
-- INNER JOIN: solo filas que coinciden en ambas tablas
SELECT e.nombre, d.nombre AS departamento
FROM   empleados e
INNER JOIN departamentos d ON e.id_depto = d.id;

-- LEFT JOIN: todas las filas de la izquierda, NULL si no hay match
SELECT e.nombre, d.nombre AS departamento
FROM   empleados e
LEFT JOIN departamentos d ON e.id_depto = d.id;

-- GROUP BY + HAVING
SELECT   d.nombre, COUNT(e.id) AS total, AVG(e.salario) AS promedio
FROM     empleados e
JOIN     departamentos d ON e.id_depto = d.id
GROUP BY d.nombre
HAVING   COUNT(e.id) > 3
ORDER BY promedio DESC;
\end{lstlisting}

\end{enumerate}
\end{entrevistabox}
