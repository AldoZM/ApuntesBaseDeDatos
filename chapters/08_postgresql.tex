\chapter{PostgreSQL --- Características Avanzadas}

\section[Por qué PostgreSQL]{\emj{🧠}~Por qué PostgreSQL}

PostgreSQL es el RDBMS open source más completo y conforme al estándar SQL.
A diferencia de MySQL, es extensible por diseño: cualquiera puede agregar tipos de dato, operadores, funciones y métodos de acceso mediante extensiones.
Su MVCC robusto, soporte nativo de JSON, y herramientas de administración maduras lo hacen la primera opción para aplicaciones nuevas.

\begin{teoriabox}{Arquitectura de PostgreSQL}
\begin{itemize}
  \item \textbf{Proceso postmaster:} proceso padre que gestiona conexiones; cada cliente obtiene su propio proceso hijo
  \item \textbf{WAL (Write-Ahead Log):} todos los cambios se escriben al log antes de modificar los datos; garantiza durabilidad y permite PITR
  \item \textbf{MVCC:} cada fila tiene versiones; lecturas ven el snapshot de su transacción sin bloquear escrituras
  \item \textbf{Shared Buffer Cache:} pool de memoria compartida para páginas de disco; \texttt{shared\_buffers} controla su tamaño (típico: 25\% de RAM)
  \item \textbf{Autovacuum:} proceso en background que recicla versiones muertas de filas (generadas por MVCC)
\end{itemize}
\end{teoriabox}

\begin{itemize}
  \item JSONB: JSON binario indexable (vs JSON texto, que no puede usar índices GIN)
  \item Extensiones: PostGIS (geo), pg\_trgm (trigrams/búsqueda difusa), uuid-ossp, pgcrypto
  \item VACUUM: recupera espacio de filas muertas que deja el MVCC
  \item Roles: sistema de permisos basado en roles heredables, no usuarios individuales
  \item Particionamiento nativo: RANGE, LIST, HASH (PG 10+)
\end{itemize}

\section[JSONB]{\emj{🧠}~JSONB}

JSONB almacena JSON en formato binario descompuesto: lo parsea al insertar y guarda la estructura interna.
Esto permite índices GIN y operadores de búsqueda que JSON texto no soporta.
Usar JSONB cuando el dato es inherentemente semiestructurado; no como sustituto de columnas relacionales bien definidas.

\begin{itemize}
  \item \texttt{->} devuelve JSON (objeto/array) --- útil para extraer subobjetos
  \item \texttt{->>} devuelve texto --- para comparaciones con \texttt{WHERE}
  \item \texttt{@>} contiene (compatible con índice GIN) --- operador más importante
  \item \texttt{?} tiene la clave --- verificar existencia sin importar el valor
\end{itemize}

\section[VACUUM y mantenimiento]{\emj{🧠}~VACUUM y mantenimiento}

El MVCC de PostgreSQL crea \emph{versiones muertas} de filas al hacer \texttt{UPDATE} o \texttt{DELETE}: la fila antigua queda en el heap pero invisible para nuevas transacciones.
VACUUM recupera ese espacio. Sin VACUUM periódico, la tabla crece indefinidamente (table bloat) y el planificador trabaja con estadísticas desactualizadas.

\begin{warningbox}{VACUUM FULL en producción}
\texttt{VACUUM FULL} compacta la tabla reescribiéndola desde cero, liberando el espacio al SO.
El problema: bloquea la tabla con un lock exclusivo durante todo el proceso.
En producción, prefiere \texttt{VACUUM} regular (que solo marca espacio como reutilizable sin bloquear) y reserva \texttt{VACUUM FULL} para ventanas de mantenimiento planificadas.
\end{warningbox}

\begin{lstlisting}[caption={JSONB --- consultas y operadores}]
CREATE TABLE eventos (
    id      SERIAL PRIMARY KEY,
    datos   JSONB NOT NULL,
    creado  TIMESTAMP DEFAULT NOW()
);

INSERT INTO eventos (datos) VALUES
  ('{"tipo": "login", "usuario": "ana", "ip": "192.168.1.1"}'),
  ('{"tipo": "compra", "usuario": "carlos", "monto": 350.00}');

-- Acceder a campos
SELECT datos->>'usuario' AS usuario, datos->>'tipo' AS tipo
FROM eventos;

-- Filtrar con @> (usa índice GIN)
CREATE INDEX idx_eventos_gin ON eventos USING GIN(datos);
SELECT * FROM eventos WHERE datos @> '{"tipo": "login"}';

-- Actualizar campo en JSONB
UPDATE eventos
SET datos = datos || '{"procesado": true}'::jsonb
WHERE datos->>'tipo' = 'compra';
\end{lstlisting}

\begin{lstlisting}[caption={Roles, permisos y VACUUM}]
-- Crear rol de solo lectura
CREATE ROLE readonly;
GRANT CONNECT ON DATABASE mibd TO readonly;
GRANT USAGE ON SCHEMA public TO readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly;

-- Crear usuario con ese rol
CREATE USER reportes_user WITH PASSWORD 'segura123';
GRANT readonly TO reportes_user;

-- VACUUM manual
VACUUM ANALYZE empleados;

-- Ver tablas que necesitan vacuum
SELECT relname, n_dead_tup, last_vacuum
FROM   pg_stat_user_tables
WHERE  n_dead_tup > 10000
ORDER BY n_dead_tup DESC;
\end{lstlisting}

\begin{lstlisting}[caption={Particionamiento nativo en PostgreSQL}]
-- Tabla particionada por rango de fecha
CREATE TABLE ventas (
    id      SERIAL,
    fecha   DATE NOT NULL,
    monto   NUMERIC(10,2),
    region  VARCHAR(50),
    PRIMARY KEY (id, fecha)
) PARTITION BY RANGE (fecha);

-- Crear particiones
CREATE TABLE ventas_2023 PARTITION OF ventas
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE ventas_2024 PARTITION OF ventas
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

-- PostgreSQL enruta automáticamente al insertar
INSERT INTO ventas (fecha, monto, region)
VALUES ('2024-06-15', 5000.00, 'Norte');
\end{lstlisting}
