\chapter{Transacciones y Control de Concurrencia}

\section[ACID]{\emj{🧠}~ACID}

Una transacción es un conjunto de operaciones que se ejecutan como una unidad indivisible.
ACID es el conjunto de propiedades que garantizan que las transacciones son confiables incluso ante fallos del sistema o acceso concurrente.
Estas propiedades son el fundamento de cualquier sistema financiero, de inventario o de misión crítica.

\begin{teoriabox}{ACID explicado con transferencia bancaria}
Transferir \$1000 de la cuenta A a la cuenta B involucra dos operaciones:
(1) restar \$1000 de A y (2) sumar \$1000 a B.

\begin{itemize}
  \item \textbf{Atomicidad:} si el sistema falla entre (1) y (2), se revierten ambas. Nunca el dinero desaparece ``a la mitad''.
  \item \textbf{Consistencia:} la suma total del dinero en el sistema es la misma antes y después. Los constraints (saldo $\geq 0$) se respetan.
  \item \textbf{Aislamiento:} otra transacción que consulte el saldo de A durante la transferencia no ve el estado intermedio.
  \item \textbf{Durabilidad:} una vez que el COMMIT se confirma, los cambios persisten aunque el servidor se apague inmediatamente después (gracias al WAL).
\end{itemize}
\end{teoriabox}

\section[Niveles de aislamiento]{\emj{🧠}~Niveles de aislamiento}

El aislamiento tiene un costo: mayor aislamiento implica más locks y menor concurrencia.
El estándar SQL define cuatro niveles; PostgreSQL implementa tres efectivos (Read Uncommitted se comporta como Read Committed).

\begin{itemize}
  \item \textbf{Read Uncommitted:} no existe en PG (se comporta como Read Committed)
  \item \textbf{Read Committed:} default en PG. Ve solo datos confirmados. Sujeto a \emph{non-repeatable reads}.
  \item \textbf{Repeatable Read:} la misma fila devuelve el mismo valor en toda la transacción. Previene non-repeatable reads.
  \item \textbf{Serializable:} aislamiento total equivalente a ejecución serial. Más lento; detecta anomalías serializables.
\end{itemize}

\begin{tipbox}{¿Qué nivel usar?}
\textbf{Read Committed} cubre el 95\% de los casos.
Usa \textbf{Repeatable Read} cuando una transacción hace múltiples lecturas de los mismos datos y necesita consistencia (reportes financieros).
Usa \textbf{Serializable} solo cuando la correctitud lógica lo exija; tiene overhead significativo.
\end{tipbox}

\section[Locks y Deadlocks]{\emj{🧠}~Locks y Deadlocks}

PostgreSQL usa MVCC (Multi-Version Concurrency Control): las lecturas nunca bloquean escrituras y las escrituras nunca bloquean lecturas.
Cada transacción ve un snapshot consistente de la BD al momento de inicio.
Los deadlocks ocurren cuando dos transacciones se esperan mutuamente; PostgreSQL los detecta y aborta la más joven.

\begin{warningbox}{Deadlocks y cómo prevenirlos}
El deadlock clásico: T1 bloquea fila A y espera la B; T2 bloquea fila B y espera la A.
Prevención: acceder siempre a los recursos en el \textbf{mismo orden} en todas las transacciones.
Si T1 y T2 siempre bloquean A antes que B, el deadlock es imposible.
\end{warningbox}

\begin{lstlisting}[caption={BEGIN, COMMIT, ROLLBACK, SAVEPOINT}]
BEGIN;

UPDATE cuentas SET saldo = saldo - 1000 WHERE id = 1;
UPDATE cuentas SET saldo = saldo + 1000 WHERE id = 2;

-- Si algo falla:
ROLLBACK;
-- Si todo OK:
COMMIT;

-- SAVEPOINT: rollback parcial
BEGIN;
UPDATE inventario SET stock = stock - 5 WHERE producto_id = 10;
SAVEPOINT antes_descuento;
UPDATE precios SET precio = precio * 0.9 WHERE producto_id = 10;
ROLLBACK TO SAVEPOINT antes_descuento;
COMMIT;
\end{lstlisting}

\begin{lstlisting}[caption={SELECT FOR UPDATE y nivel de aislamiento}]
-- Bloquear fila para actualización (evita race condition)
BEGIN;
SELECT saldo FROM cuentas WHERE id = 1 FOR UPDATE;
UPDATE cuentas SET saldo = saldo - 500 WHERE id = 1;
COMMIT;

-- Cambiar nivel de aislamiento
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT total FROM reporte WHERE mes = '2024-01';
COMMIT;
\end{lstlisting}

\begin{lstlisting}[caption={Detectar y matar conexiones colgadas}]
-- Ver transacciones activas hace más de 5 minutos
SELECT pid, usename, state, query_start,
       NOW() - query_start AS duracion,
       LEFT(query, 80) AS query_corta
FROM   pg_stat_activity
WHERE  state != 'idle'
  AND  query_start < NOW() - INTERVAL '5 minutes';

-- Terminar transacción colgada
SELECT pg_terminate_backend(12345);
\end{lstlisting}
