\section[Backups]{\emj{💾}~Backups}

El backup es la operación más importante de la administración de bases de datos y, paradójicamente, la más frecuentemente ignorada hasta que ocurre un desastre.
La regla más importante: \textbf{un backup no probado no existe}.
Un dump corrupto, incompleto o que no puede restaurarse es exactamente igual a no tener backup.

PostgreSQL ofrece dos niveles de backup con propósitos distintos:
\begin{itemize}
  \item \textbf{Backup lógico}: extrae los datos como SQL o en formato binario propio de PostgreSQL.
    Portable entre versiones y sistemas operativos. Puede restaurar tablas o bases individuales.
    Herramientas: \texttt{pg\_dump} (una BD) y \texttt{pg\_dumpall} (todo el cluster + roles globales).
  \item \textbf{Backup físico}: copia los archivos binarios del cluster de PostgreSQL tal como están en disco.
    Más rápido para BDs grandes. Requiere la misma versión de PostgreSQL al restaurar.
    Herramienta: \texttt{pg\_basebackup}. Necesario para Point-In-Time Recovery (PITR).
\end{itemize}

\begin{teoriabox}{Estrategia de backup recomendada}
Una estrategia robusta combina ambos tipos:
\begin{itemize}
  \item \textbf{pg\_basebackup semanal:} copia física completa del cluster. Base para PITR.
  \item \textbf{WAL Archiving continuo:} archiva cada segmento de WAL (16MB cada uno) a un almacenamiento externo. Permite restaurar a cualquier segundo entre el último basebackup y ahora.
  \item \textbf{pg\_dump diario por BD crítica:} backup lógico para restauración selectiva de tablas, más fácil de hacer en ambientes de desarrollo/staging.
\end{itemize}
\textbf{Prueba de restauración mensual:} restaurar un backup en un servidor de prueba y verificar que los datos son correctos y la aplicación funciona.
Sin esta prueba, no sabes si el backup funciona hasta que lo necesitas en producción.
\end{teoriabox}

\begin{warningbox}{Errores comunes en backups}
\begin{itemize}
  \item Backups en el mismo disco que los datos: si el disco falla, se pierde todo.
  \item No incluir \texttt{pg\_dumpall} en la estrategia: los roles y tablespaces globales solo existen ahí.
  \item Usar \texttt{VACUUM FULL} en producción sin planificación: bloquea la tabla completamente mientras reescribe; puede durar horas en tablas grandes.
  \item Confiar en \texttt{pg\_dump} solo: sin WAL archiving, el RPO (punto de recuperación) es el momento del último dump, que puede ser hace 24 horas.
\end{itemize}
\end{warningbox}

\section[Usuarios, roles y permisos]{\emj{🔐}~Usuarios, roles y permisos}

PostgreSQL usa \textbf{roles} como unidad unificada de identidad y permisos.
Un rol con el atributo \texttt{LOGIN} es lo que coloquialmente llamamos ``usuario''; sin ese atributo, es un grupo de permisos que se asigna a otros roles.
Esta unificación simplifica la administración: en lugar de gestionar usuarios y grupos por separado, todo es un rol.

El modelo de permisos en PostgreSQL es \textbf{jerárquico y aditivo}:
un rol hereda los permisos de todos los roles que se le asignan.
Esto permite construir una jerarquía: rol \texttt{readonly} → se asigna a \texttt{reportes\_user}; si además se necesita escritura, se asigna \texttt{readwrite} al mismo usuario sin quitar nada.

El \textbf{principio de mínimo privilegio} dicta que cada rol tenga exactamente los permisos que necesita para su función, ni más.
Una aplicación web que solo lee datos no debe tener permiso de DROP TABLE.
Un usuario de reportes no debe poder INSERT.
Esto limita el daño en caso de compromiso de credenciales o bug en la aplicación.

Los permisos se otorgan a distintos niveles de granularidad:
\begin{itemize}
  \item \textbf{Conexión a BD:} \texttt{GRANT CONNECT ON DATABASE}
  \item \textbf{Uso de schema:} \texttt{GRANT USAGE ON SCHEMA}
  \item \textbf{Tablas:} \texttt{GRANT SELECT, INSERT, UPDATE, DELETE ON TABLE}
  \item \textbf{Columnas:} \texttt{GRANT SELECT (col1, col2) ON TABLE} — oculta columnas sensibles
  \item \textbf{Filas:} Row Level Security (RLS) — cada fila puede tener su propia política de acceso
\end{itemize}

\section[Monitoreo básico]{\emj{📊}~Monitoreo básico}

El monitoreo de una base de datos tiene dos objetivos: detectar problemas \emph{antes} de que impacten al usuario (monitoreo proactivo) y diagnosticar problemas cuando ya ocurrieron (monitoreo reactivo).
Las vistas del sistema de PostgreSQL ofrecen visibilidad en tiempo real sin necesidad de herramientas externas.

Las señales de alerta más importantes a monitorear continuamente:
\begin{itemize}
  \item \textbf{Conexiones activas:} si se acerca al límite de \texttt{max\_connections}, nuevas conexiones son rechazadas. Considera un connection pooler (PgBouncer).
  \item \textbf{Transacciones largas:} una transacción abierta por horas bloquea el VACUUM y acumula bloat. Detectar y terminar las idle in transaction es crítico.
  \item \textbf{Dead tuples:} filas muertas acumuladas por MVCC. Si autovacuum no las limpia a tiempo, la tabla crece sin control y las queries se vuelven lentas.
  \item \textbf{Queries lentas:} con \texttt{pg\_stat\_statements}, identificar las queries con mayor tiempo total de ejecución y optimizarlas.
  \item \textbf{Locks:} un lock no otorgado (waiting) indica contención. Si se acumula una cadena de locks, puede paralizar la aplicación.
\end{itemize}

\begin{lstlisting}[caption={Backups con pg\_dump y restauración}]
-- Backup lógico (formato custom, comprimido)
pg_dump -U postgres -Fc -f backup_mibd_20260516.dump mibd

-- Backup lógico en SQL plano
pg_dump -U postgres -f backup_mibd.sql mibd

-- Restaurar desde formato custom
pg_restore -U postgres -d mibd_nueva backup_mibd_20260516.dump

-- Restaurar SQL plano
psql -U postgres -d mibd_nueva -f backup_mibd.sql

-- Backup de todas las bases + roles globales
pg_dumpall -U postgres -f cluster_completo.sql
\end{lstlisting}

\begin{lstlisting}[caption={Monitoreo --- conexiones, locks y queries lentas}]
-- Conexiones activas
SELECT pid, usename, state, query_start,
       LEFT(query, 100) AS query_corta
FROM   pg_stat_activity
WHERE  state != 'idle'
ORDER BY query_start;

-- Terminar conexión colgada
SELECT pg_terminate_backend(pid)
FROM   pg_stat_activity
WHERE  state = 'idle in transaction'
  AND  query_start < NOW() - INTERVAL '10 minutes';

-- Ver locks activos
SELECT pid, relation::regclass, mode, granted
FROM   pg_locks
WHERE  NOT granted;
\end{lstlisting}

\begin{lstlisting}[caption={pg\_stat\_statements --- queries más lentas}]
-- Activar extensión (requiere superuser, reinicio de PG)
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 queries más lentas por tiempo promedio
SELECT LEFT(query, 120) AS query,
       calls,
       ROUND((total_exec_time / calls)::numeric, 2) AS avg_ms,
       ROUND(total_exec_time::numeric, 2) AS total_ms
FROM   pg_stat_statements
ORDER BY avg_ms DESC
LIMIT  10;

-- Resetear estadísticas
SELECT pg_stat_statements_reset();
\end{lstlisting}
