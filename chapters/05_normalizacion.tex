\chapter[Normalización]{\emj{🧹}~Normalización}

\section[¿Por qué normalizar?]{\emj{🧠}~¿Por qué normalizar?}

La normalización es un proceso sistemático de diseño de esquemas relacionales que elimina redundancia y las anomalías que esta produce.
Fue formalizada por E.F.~Codd junto con el modelo relacional y se basa en el concepto de \textbf{dependencias funcionales}: cómo los valores de ciertos atributos determinan los valores de otros.

El problema de la redundancia es sutil: la misma información almacenada en múltiples lugares no es solo un desperdicio de espacio, sino una fuente de inconsistencia.
Cuando el mismo dato está en muchas filas, cualquier actualización debe propagarse a todas ellas.
Si falla a la mitad, la BD queda en estado inconsistente sin que el DBMS lo detecte (porque cada fila individualmente es válida).

\begin{teoriabox}{Las tres anomalías de la desnormalización}
Considera una tabla \texttt{empleado\_depto(id\_emp, nombre\_emp, id\_depto, nombre\_depto, salario)} donde \texttt{nombre\_depto} depende de \texttt{id\_depto}, no de \texttt{id\_emp}:

\begin{itemize}
  \item \textbf{Anomalía de inserción:} es imposible registrar un departamento nuevo sin tener al menos un empleado en él, porque \texttt{nombre\_depto} solo existe junto a \texttt{id\_emp}.
  \item \textbf{Anomalía de actualización:} si el departamento ``Ingeniería'' cambia de nombre a ``Tecnología'', hay que actualizar \emph{cada fila} de cada empleado de ese depto. Si se actualiza solo parte, la BD tiene dos nombres distintos para el mismo departamento.
  \item \textbf{Anomalía de borrado:} si el último empleado del departamento ``Marketing'' deja la empresa y se borra su fila, se pierde toda la información del departamento ``Marketing'' junto con ella.
\end{itemize}
La solución a las tres anomalías es la misma: separar cada entidad en su propia tabla y usar FK para relacionarlas.
\end{teoriabox}

\section[Formas normales]{\emj{📋}~Formas normales}

Las formas normales son criterios progresivos de diseño, donde cada nivel incluye al anterior y agrega una restricción más específica.
No son reglas arbitrarias: cada forma normal elimina una categoría específica de anomalía.
En la práctica, 3NF es el objetivo estándar para bases de datos transaccionales (OLTP).

\begin{itemize}
  \item \textbf{1NF (Primera Forma Normal):}
    Cada celda contiene un valor atómico (no listas, no arrays, no múltiples valores separados por coma).
    No hay filas duplicadas. La tabla tiene una PK definida.
    Violación clásica: columna \texttt{telefonos} con valor ``555-1234, 555-5678''.

  \item \textbf{2NF (Segunda Forma Normal):}
    En 1NF + cada atributo no-clave depende de \emph{toda} la PK compuesta, no solo de una parte.
    Solo aplica cuando la PK está formada por múltiples columnas (PK compuesta).
    Violación: tabla con PK=(id\_pedido, id\_producto) y una columna \texttt{nombre\_producto} que depende solo de \texttt{id\_producto}.

  \item \textbf{3NF (Tercera Forma Normal):}
    En 2NF + ningún atributo no-clave depende transitivamente de otro atributo no-clave.
    Violación: tabla con \texttt{id\_depto} $\to$ \texttt{nombre\_depto}, donde ambos son atributos no-clave.
    El atributo \texttt{nombre\_depto} depende de \texttt{id\_depto}, no directamente de la PK.

  \item \textbf{BCNF (Boyce-Codd Normal Form):}
    Más estricta que 3NF: todo determinante debe ser una superkey.
    Cubre casos extremos donde 3NF no es suficiente (relaciones con múltiples candidate keys superpuestas).
\end{itemize}

\begin{tipbox}{¿Cuándo desnormalizar intencionalmente?}
La desnormalización sacrifica integridad por rendimiento y es válida en contextos específicos:
\begin{itemize}
  \item \textbf{Data Warehouses (OLAP):} star schema y snowflake schema desnormalizan intencionalmente para evitar joins costosos en queries de millones de filas.
  \item \textbf{Cachés de lectura:} tablas desnormalizadas para reportes frecuentes que se actualizan por batch.
  \item \textbf{Campos calculados persistidos:} cuando recalcular en cada consulta es más costoso que mantener la redundancia con un trigger.
\end{itemize}
Desnormalizar siempre debe ser una decisión consciente y documentada, nunca por accidente.
\end{tipbox}

\section[Dependencias funcionales]{\emj{🔗}~Dependencias funcionales}

Una dependencia funcional $X \rightarrow Y$ significa: conocer el valor de $X$ determina unívocamente el valor de $Y$.
Es la herramienta matemática para razonar sobre la normalización: identificar dependencias funcionales en un esquema es equivalente a identificar qué forma normal tiene.

Ejemplos concretos:
\begin{itemize}
  \item \texttt{id\_empleado} $\rightarrow$ \texttt{nombre\_empleado}: saber el id determina el nombre (dependencia total de la PK — correcto en 2NF)
  \item \texttt{id\_producto} $\rightarrow$ \texttt{nombre\_producto} dentro de PK=(id\_pedido, id\_producto): dependencia \textbf{parcial} — viola 2NF
  \item \texttt{id\_depto} $\rightarrow$ \texttt{nombre\_depto} donde \texttt{id\_depto} no es clave: dependencia \textbf{transitiva} — viola 3NF
\end{itemize}

Si \textbf{PK = \{A, B\}} y existe $A \rightarrow C$ (C no depende de B) → dependencia \textbf{parcial} → viola 2NF.

Si existe no-clave $\rightarrow$ no-clave (por ejemplo \texttt{id\_depto} $\rightarrow$ \texttt{nombre\_depto}) → dependencia \textbf{transitiva} → viola 3NF.

\begin{lstlisting}[caption={Tabla que viola 2NF y su corrección}]
-- VIOLA 2NF: PK=(id_pedido, id_producto) pero nombre_producto
--            depende solo de id_producto (dependencia parcial)
CREATE TABLE pedido_items_malo (
    id_pedido       INTEGER,
    id_producto     INTEGER,
    nombre_producto VARCHAR(100),
    cantidad        INTEGER,
    PRIMARY KEY (id_pedido, id_producto)
);

-- CORRECTO: separar producto a su propia tabla
CREATE TABLE productos (
    id     SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL
);

CREATE TABLE pedido_items (
    id_pedido   INTEGER,
    id_producto INTEGER REFERENCES productos(id),
    cantidad    INTEGER NOT NULL,
    PRIMARY KEY (id_pedido, id_producto)
);
\end{lstlisting}

\begin{lstlisting}[caption={Tabla que viola 3NF y su corrección}]
-- VIOLA 3NF: id_depto -> nombre_depto (dependencia transitiva)
CREATE TABLE empleados_malo (
    id_empleado  SERIAL PRIMARY KEY,
    nombre       VARCHAR(100),
    id_depto     INTEGER,
    nombre_depto VARCHAR(80)
);

-- CORRECTO: tabla separada para departamentos
CREATE TABLE departamentos (
    id     SERIAL PRIMARY KEY,
    nombre VARCHAR(80) NOT NULL
);

CREATE TABLE empleados (
    id       SERIAL PRIMARY KEY,
    nombre   VARCHAR(100),
    id_depto INTEGER REFERENCES departamentos(id)
);
\end{lstlisting}

\begin{entrevistabox}
\begin{enumerate}
  \item ¿Cuál es la diferencia entre 2NF y 3NF?
  \item ¿Cuándo desnormalizarías intencionalmente una tabla?
  \item Identifica la forma normal: \texttt{(orden\_id, producto\_id, categoria\_producto, cantidad)} con PK=(orden\_id, producto\_id).
\end{enumerate}
\end{entrevistabox}
